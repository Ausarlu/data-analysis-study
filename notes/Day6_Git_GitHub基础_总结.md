# Day 6 学习总结：Git / GitHub 基础

## 一、核心概念：Git 是什么，GitHub 是什么

- **Git**：安装在本地电脑上的版本控制软件，负责记录一个项目文件夹里文件的历史变化，可以随时回到之前的某个版本
- **GitHub**：一个网站/云端平台，让本地Git管理的项目可以上传备份、分享、多人协作
- 类比：Git像文档的"修订记录"功能（工具本身），GitHub像"云盘"（存储和分享的平台）。Git是工具，GitHub是使用这个工具的其中一个云端服务商（还有GitLab、Bitbucket等同类平台）

---

## 二、Git 内部的三层结构：工作目录 → 暂存区 → 仓库

### 不是物理上分开的三个文件夹，而是同一批文件在Git系统里的三种状态/记录机制

- **工作目录（Working Directory）**：唯一能直接看到、编辑的完整文件本身，一直待在原位不会被"移动"
- **暂存区（Staging Area）**：不是文件的完整副本，更接近"一份清单/标记"，记录"这次commit要包含哪些改动"；`git add` 把改动放进暂存区
- **仓库（Repository）**：Git自己的一套历史数据库（存在隐藏的`.git`文件夹里），真正保存每次commit时的完整快照；`git commit` 把暂存区内容正式写入仓库历史

### 完整流程
```
工作目录（编辑文件） → git add → 暂存区（标记这次要提交什么） → git commit → 仓库（正式写入历史，本地永久保存）→ git push → GitHub（上传云端）
```

### 类比
工作目录=书桌上正在写的稿子；暂存区=贴便利贴标记"这几段这次要存档"；仓库(commit后)=正式装订成册存入书架；push到GitHub=送一份到云端图书馆备份

---

## 三、分支（Branch）—— 原计划未包含，学习者主动要求加入

- 每个仓库默认有一条分支，叫 `main`（早期习惯叫`master`，现在GitHub默认用`main`）
- **分支 = 从某个commit点分叉出的独立历史时间线**，在新分支上commit不会影响原分支
- 用途：安全尝试新东西（失败可直接删除分支，不影响main）；多人协作互不干扰各自开发
- **合并（Merge）**：把一个分支的改动，并回另一个分支（`git merge`）
- **合并冲突**：两个分支改了同一处地方时，Git无法自动判断，需要手动决定保留哪部分（概念先了解，具体操作留到实际遇到时再学）
- 类比：main分支是"正史"，新分支是可以随意折腾的"平行时空"，成功了合并回正史，失败了直接关掉，正史不受影响

## 四、Git 命令记忆原则

不需要死记硬背所有命令，区分两类：
- **一次性配置命令**（如设置用户名邮箱、身份验证配置）：理解"这一步在做什么"就够，具体怎么打现场查/问即可
- **高频重复使用的核心命令**（add/commit/push/pull）：值得多练，用几次自然就记住，不需要专门背

## 五、实操步骤记录（含踩坑与排查过程）

### 1. 环境准备
```bash
git --version                              # 检查是否已安装
git config --global user.name "你的名字"    # 设置提交时显示的用户名（一次性）
git config --global user.email "你的邮箱"   # 设置邮箱，建议与GitHub账号一致
```

### 2. 创建本地仓库 —— 务必先确认所在目录
```bash
cd /路径/到/你的项目文件夹     # 一定要先cd进正确的项目文件夹！
pwd                          # 确认当前路径
git init                     # 初始化仓库，创建隐藏的.git文件夹
```
**踩坑记录**：曾误在用户主目录（`/Users/luli`，而非项目文件夹）执行`git init`，导致大量系统级文件（.vscode/.jupyter等）被显示为"Untracked"。发现后用 `rm -rf .git` 精确删除了误建的仓库文件夹（不影响其他文件），重新`cd`到正确路径后再`git init`。**教训：每次git init前，务必先pwd确认路径**。

### 3. `.gitignore`：告诉Git永远不要追踪的文件
- 在项目文件夹内新建一个文件，文件名固定为 `.gitignore`（开头有点，隐藏文件命名方式）
- 常见规则示例：
```
.DS_Store           # Mac系统自动生成的垃圾文件
__pycache__/        # Python缓存文件夹（结尾/表示整个文件夹忽略）
*.pyc               # 通配符*匹配任意字符，忽略所有.pyc文件
.ipynb_checkpoints/ # Jupyter自动生成的快照文件夹
```
- 过滤发生在 `git add` **执行之前**：被忽略的文件根本不会经过"放入暂存区"这个过程，不是"先加入再移出"

### 4. 查看状态：`git status`
- 本质是做**两组相邻比较**：①暂存区 vs 仓库最新commit记录 ②工作目录 vs 暂存区（"仓库vs工作目录"的结果可以从这两组推导出来，不需要单独比较）
- 常见提示语含义：
  - `Untracked files`：文件存在于工作目录，但Git完全不知道它的存在（从未被add过）
  - `Changes to be committed`：文件已经进入暂存区，等待commit
  - `nothing to commit, working tree clean`：工作目录、暂存区、仓库三者内容一致，没有任何待处理的差异

### 5. 添加到暂存区：`git add`
```bash
git add .          # 点号代表当前文件夹下所有未被忽略的文件
git add 文件名       # 只添加指定的某个文件
```

### 6. 提交到仓库：`git commit`
```bash
git commit -m "提交说明文字"
```
- `-m` 后面必须写提交说明（不写`-m`会跳出编辑器要求输入，说明不能为空）——这段文字会被永久保存进commit历史，不同于代码里可有可无的`#`注释
- commit完成后，暂存区会被清空（不是"东西丢失"，而是这份改动已经正式转移、升级进了仓库的永久历史）

### 7. 连接远程仓库并推送
- 先在GitHub网站创建一个新仓库（New repository），获得仓库地址（形如 `https://github.com/用户名/仓库名.git`）
```bash
git remote add origin 仓库地址URL    # origin是约定俗成的远程仓库别名
git remote -v                        # 验证连接是否设置成功
git push -u origin main              # 首次推送，-u建立本地main与远程main的关联，之后可简写为 git push
```

**踩坑记录：身份验证问题**
- GitHub自2021年起不再支持用登录密码做Git操作验证，必须用"个人访问令牌"（Personal Access Token, PAT）代替密码
- 生成路径：`github.com/settings/tokens` → Generate new token (classic) → 命名、设置过期时间、**务必勾选`repo`权限** → Generate token
- 生成后立刻复制保存（页面刷新后无法再次查看原文），推荐用页面自带的复制按钮而非手动选中拖拽，避免复制不完整
- push时终端依次提示输入Username（GitHub用户名）和Password（此处粘贴token，不是登录密码），粘贴时终端不会显示任何字符（正常的安全设计，不代表没输入成功）
- 第一次因token复制/权限问题导致 `Authentication failed`，重新生成token并谨慎复制后，第二次push成功

### 8. push 推送的本质
- `git push` 推送的是**本地仓库（已commit的完整历史记录）**，不是工作目录当前的样子
- 未commit的改动，不管是否push，都完全停留在本地工作目录，不会被同步
- 项目的"时间0"是**第一次commit的那一刻**，之前对文件的任何改动（在commit之前发生的），无论本地还是云端都无法找回、无法还原——这不是功能缺陷，而是"记录"这个概念的自然边界（Git只能回放它曾经记录过的内容）
- 实际项目中不会刻意做"空提交留底"，而是养成"尽早开始commit、按正常工作节奏持续commit"的习惯，第一次commit自然就成为可追溯的最早版本
